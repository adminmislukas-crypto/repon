# Delta for core-api-ofertas

`core-api-ofertas` was archived under `2026-08-15-backend-core-api-ofertas`. This is a delta on an already-archived domain's spec — the second one this repo writes into a sibling's already-closed domain (D1), following the same additive discipline `ofertas` itself established when it extended `catalogo`'s `CatalogQueryPort` and wrote listeners inside `refill-matching`: no field removed, no existing scenario invalidated, `refill-matching`'s own `OfertaAceptadaListener` unaffected.

## ADDED Requirements

### Requirement: enviarOferta and enviarOfertaProactiva assign each line's id and nombre at composition time; the client never supplies either

Every `OfferItem` produced by `enviarOferta`/`enviarOfertaProactiva` MUST be assigned an `id` (generated by the domain, `randomUUID()`, never left to the database default — `pedidos-pagos` needs it as `order_items.offer_item_id`, `NOT NULL` with a foreign key) and a `nombre`, resolved at composition time — the same instant the line's price is frozen (D-B.2). For a reactive line, `nombre` MUST come from the matched `RefillItem` (what the user requested and the provider agreed to fulfill); for a proactive line, from the matching `ProviderCatalogItem.nombre`. Neither `NuevoOfferItem` variant MUST declare an `id` or `nombre` field — a client-writable `nombre` would let a provider place arbitrary text into a physically immutable downstream snapshot (`order_items`, no `UPDATE`/`DELETE` for any role).

#### Scenario: A reactive line's nombre comes from the requested RefillItem, not the catalog

- GIVEN a reactive offer composed from a solicitud whose `RefillItem` I has `nombre: "Agua 20L"`
- WHEN `enviarOferta` composes the line matching I
- THEN the resulting `OfferItem.nombre` is `"Agua 20L"`, regardless of what the provider's own catalog calls the equivalent product

#### Scenario: A proactive line's nombre comes from the provider's catalog listing

- GIVEN `enviarOfertaProactiva` composing a line from `ProviderCatalogItem` P with `nombre: "Bidón 10L"`
- WHEN the offer is composed
- THEN the resulting `OfferItem.nombre` is `"Bidón 10L"`

#### Scenario: The client cannot submit a nombre or an id

- GIVEN `NuevoOfferItemReactiva`/`NuevoOfferItemProactiva`'s fields
- WHEN they are enumerated
- THEN neither declares `nombre` or `id` — both are assigned by the domain, never accepted from the request

## MODIFIED Requirements

### Requirement: OfertaEnviada and OfertaAceptada publish only after commit, with exactly the fields fixed by D6

`OfertaEnviada` (`'ofertas.oferta_enviada'`: `offerId`, `kind`, `companyId`, `userId`, `refillRequestId: string | null`, `total`, `tiempoEntregaHoras`) and `OfertaAceptada` (`'ofertas.oferta_aceptada'`: `offerId`, `companyId`, `userId`, `refillRequestId: string | null`, `total`, `desplazadas: readonly string[]`, `costoDespacho: number`, `lineas: readonly OfertaAceptadaLineaPayload[]`) MUST publish only after their respective transaction commits — never inside it, never before. `refillRequestId: null` marks a proactive offer/acceptance on both events.

`lineas` and `costoDespacho` — added by `backend-core-api-pedidos-pagos` (D1/D-B.4) — extend `OfertaAceptada` only. `lineas` is `ofertas`' own vocabulary describing the accepted offer's lines, never the `OfferItem` type re-exported: each entry carries `offerItemId` (→ `order_items.offer_item_id`), `nombre`, `precio` (→ both `precio_unitario` and `subtotal` downstream, since `cantidad` is always 1), `isAlt`, `altSize?`, `altQty?`, `altNote?`. `costoDespacho` is copied from `offers.costo_despacho` unchanged. This is additive: `refill-matching`'s `OfertaAceptadaListener` redeclares its own local payload type reading only `refillRequestId`, so the new fields are invisible to it and require no change there.

(Previously: `OfertaAceptada` carried only `offerId`, `companyId`, `userId`, `refillRequestId`, `total`, `desplazadas` — no line-level detail and no shipping cost.)

#### Scenario: A proactive OfertaEnviada carries refillRequestId: null

- GIVEN `enviarOfertaProactiva` succeeds
- WHEN `OfertaEnviada` publishes
- THEN its `refillRequestId` is `null`

#### Scenario: OfertaAceptada's desplazadas lists exactly the displaced offerIds

- GIVEN accepting offer B displaced siblings A and C
- WHEN `OfertaAceptada` publishes
- THEN `desplazadas` is `[A, C]` — exactly the offers this operation moved to `'rechazada'`, and nothing more

#### Scenario: OfertaAceptada carries one line per accepted offer item, with the accepted price

- GIVEN offer O has 2 `OfferItem`s with `precio` 1000 and 2000, and `offers.costo_despacho = 500`
- WHEN O is accepted and `OfertaAceptada` publishes
- THEN `lineas` has exactly 2 entries, each with `precio` matching its source item, and `costoDespacho` is `500`

#### Scenario: refill-matching's listener is unaffected by the new fields

- GIVEN `refill-matching`'s `OfertaAceptadaListener` and its own local payload type
- WHEN `OfertaAceptada` now includes `lineas`/`costoDespacho`
- THEN the listener's behavior is unchanged — its local type declares only the fields it reads, and it compiles regardless of the payload's new fields
